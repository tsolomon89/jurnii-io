## Ontology drift

Fields that exist because of implementation convenience rather than the business model, and naming that should be fixed by **LABEL rename only** — no field change, no code change, no data migration.

### B. Fields that exist for implementation convenience, not the business model

1. **`Tasks.Blocks_Sequence`** — pure implementation state. It never described a business fact; it cached a predicate the code can compute, and the cache **drifted**: 216/219 are `Yes` (98.6% degenerate), it is never cleared when a Task completes (4 Completed/Won/Closed Tasks still carry `Yes`), and one live managed Task (`991103000002920013`, `Status=Deferred`, `Blocks_Sequence=Yes`) would block its Contact's cadence permanently under the stored read. Retiring it is **behaviour-improving**, not merely neutral. Its 3 `No` values were stamped at create in the same write that set `Status=Deferred` — a create-time echo of a decision already encoded elsewhere.
2. **`Deals.Deal_Primary_Contact`** — created to name a concept (`Contact_Name` already carries) and never wired up. Its only ever write targeted a phantom api_name. Three readers were written against it and all three immediately fall through. A field that has never held a value in 96 Deals is not part of the ontology.
3. **The nine `*_Pipeline` / `*_Opportunity` / `*_Stage` mirrors on Activities** — created so a rep could see Deal context on a Task/Call/Event row without navigating. That is a **layout convenience**, not a business fact… *except* that the convenience has silently accrued genuine history: 33/182 `Task_Opportunity` values and 6/182 `Task_Stage` values now disagree with their Deal, because the Deal climbed under the never-regress + RTP floor while the Task froze at create. **The owner's settled KEEP converts them from accidental drift into a deliberate audit trail** — which is the right call, but it should now be documented as intentional ("Deal context as of when this work was raised") rather than left looking like duplication. Recommend a layout section rename to **"Deal Context (as raised)"** on all three modules.
4. **`Events.Reminder_Send_At`** — a per-meeting computation that exists because `Deals.Demo_Reminder_Send_At` is a single scalar overwritten by every subsequent meeting. It is convenience *and* a genuine per-meeting record; its *absence* is meaningful (no reminder was possible). This is why it is the one open owner decision rather than a clean retirement.
5. **`Calls.Sequence_Stage`'s dual-vocabulary picklist** — the clearest live modelling defect in the family. The field carries **both** naming generations as distinct storable actual values (`Demo Booked` *and* `Demo Confirmation`, etc.), and it is the field the supersede guard string-compares against `Contacts.Stage`. Nothing enforces which vocabulary is written. Calls has 0 records so this is latent — **remove the 4 legacy options before the first Call record exists**, or a legitimate Call will be silently cancelled as superseded.
6. **Value-space split across the stage family** — `Contacts.Stage`, `Deals.Opportunity_Stage`, `Calls.Call_Task_Stage`, `Events.Meeting_Task_Stage` and `Tasks.Task_Stage` store **legacy actuals behind renamed display labels**; `Calls.Sequence_Stage` and `Tasks.Task_Sequence_Stage` store the **new names as actuals**. Two comparisons cross that boundary — `handleCallOutcome:91` and `handleTaskCompletion:113` — and work only because both sides currently read back in display space. This is drift from a rename that was applied to labels but not to storage. **Do not "fix" it with a bulk actual-space migration**: writing `"Renewal"`/`"Demo Confirmation"` into `Task_Stage` would write values that are not members of its actual set, corrupting 132 rows.
7. **`Tasks.Status` contains no `Cancelled` member**, yet the blocking predicate at `routeContactSequence:363`/`:1406` tests `Status != "Cancelled"`. Dead term in this org — harmless, but it signals the predicate was written against an assumed picklist rather than the live one. Same class of drift: `Task_Type ∈ {Scheduled Send, Email Sent}` is exempted by the same predicate and **no live Task has ever held either value**, so that clause is entirely untested by data.

### C. Two structural facts the ontology should record explicitly

- **`Task_Sequence_Stage` blank means "unscoped — block at every Stage"**, and `createAuxTask` never populates it. That is not an omission, it is the semantics of aux/Manual-Review Tasks. It is currently expressed only as a comment (`routeContactSequence:359`). It should be a documented field-level rule, because it is exactly the fact that makes `Task_Stage` look like a duplicate when it is not.
- **`Contacts.Sequence_Activated_At` is the only field in the family whose entire purpose is to preserve a fact that cannot be reconstructed.** Single writer, set-once, never cleared, deliberately preserved through disable, re-enable and the not-activated clamp, with a header enumerating why `Sequence_State`, `Sequence_Type` and Task existence are each untrustworthy substitutes. It is 0/647 populated — meaning **the activation engine has never run to completion in this org**, which is the single most important operational fact in this entire audit and is not itself a field problem.
